# 向非技术老板的技术汇报

## 核心判断

老板不懂技术，但他懂生意。你关心方案是否先进，他关心：**花多少钱、买的是什么、会不会出事、要不要我担责。**

一份汇报成功的唯一标准：**老板 3 分钟内能做对决策。** 做不到就是失败，写得再长再全也不算。

## 四条铁律

**铁律一：结论先行。** 第一段说完"要你批什么、值多少、花多少、什么时候要"。老板只读摘要就该能拍板。

写作工作总结式的开头（"本周技术团队围绕……开展了系列工作"）说明你在记事，不是在请示。

**铁律二：先对齐，再动笔。** 见下一节。跳过对齐直接写，产出必有编造，老板一问就穿。

**铁律三：文档独立自洽。** 汇报单独发出去，**读者手里只有这一份**。不得出现"详见某某文档""见附件""参见上次汇报""引用自 XXX"这类外部指针（见第四节）。

**铁律四：只报事实和判断，不做推销。** 见第五节。

## 一、先对齐，再动笔

### 1.1 先判缺口，不急着问

读完用户给的信息，过一遍六段，标出哪些是**空**的、哪些是**虚**的：

| 段 | 空的判定 | 虚的判定 |
|---|---|---|
| ① 一句话 | 没说清要老板批什么 | 说了"支持一下"，但没说批钱/批人/拍板 |
| ② 为什么 | 只有技术原因，没有老板能感知的场景 | 有场景但没有"为什么是现在" |
| ③ 之后 | 只有"变好了"，没落到钱/时间/风险 | 收益明显是猜的 |
| ④ 代价 | 没有数字 | 只有点估计，没说口径 |
| ⑤ 风险 | 一个字没提 | 只写了"风险可控"这种废话 |
| ⑥ 请求 | 没说要老板做什么 | 说了要什么，但没有期限和"不批的后果" |

### 1.2 一次性列完问题，别挤牙膏

**把缺的一次列完。** 三条纪律：

1. **只问真不知道的。** 用户给过的不再问。
2. **给例子照着答。** ✗"这个风险是什么？" ✓"最坏是哪种——做一半发现架构得重拆，还是人被抽走干杂活？"
3. **允许说不知道。** 不知道就标"待确认"，**留一个待确认比编一个假数字安全一百倍**。

### 1.3 六个必须问透的卡点

| 卡点 | 为什么必须问 | 怎么问 |
|---|---|---|
| 要老板做什么 | 决定整篇骨架；要钱/要人/拍板/知悉，四种写法完全不同 | "这次是批钱、批人，还是只要他知道？" |
| 不做会怎样 | 没代价就没紧迫感 | "今年不做，最坏会怎样？" |
| 为什么是现在 | 老板第一反应永远是"能不能明年" | "有什么时间点卡着？" |
| 收益是算的还是猜的 | 猜的必须标成估算 | "这数你算过还是估的？" |
| 老板最关心什么 | 决定第③段写什么 | "他最近在盯什么？上次这种事他怎么反应？" |
| 失败的底线在哪 | 决定风险段怎么写 | "做砸了最坏损失多少？能退回吗？" |

**其余细节（改了哪些模块、用什么技术）不要问**——那是附录的事。

### 1.4 口头复述一遍，确认后才动笔

用大白话把六段讲给用户听：

```
我理解要这么讲，你看对不对：
① 你要老板批 [X]
② 不做的话 [Y]
③ 做完 [Z]
④ 要花 [钱/人/时间]
⑤ 最坏 [W]
⑥ 所以请他 [在什么时间前 / 做什么]
有没有哪条不对？
```

这一步不能省。用户会在这里说出他真正的顾虑——往往是文档里最该写、他自己也没意识到的那点。

**只在两种情况下可以跳过对齐**：用户明确说"别问了直接写"，或六段全部有实打实的信息。

## 二、动笔前先取数，不留一个编造的数字

**这是本技能与一般汇报方法最大的区别：凡是数字，必须来自物料，不能来自常识。**

用户口述的数字经常与单据不符。**先看物料，再对口径，最后才写。**

| 步骤 | 做什么 |
|---|---|
| **1. 找齐物料** | 报价单（xlsx）、订单截图、付款凭证、合同、聊天记录、对标方案，问清哪份是最终版 |
| **2. 自己算一遍** | 合计、折扣、差额、占比，全部用真实数字重算，不要照抄口述 |
| **3. 逐项对口径** | 每一笔金额对应哪个产品、属于哪一类（存量/新增/配套），单台价与合价是否混用 |
| **4. 冲突时向用户摊牌** | 口述与单据不一致，**把两者摆出来让他选**，不要自己挑一个，也不要含糊带过 |
| **5. 技术事实要在系统里查证** | 涉及某功能走哪条链路、哪台机器承担什么、哪些配置变更过，去代码或配置里确认。**查不到就不写**，写明"该口径待确认" |

**示例**：用户口述"新购约 2.4 万、续费 4 万多、合计 6 万多"，报价单实为三类分项、合计远低于口述。照口述写，老板一查单据就露馅；以单据为准、把口径差异摆给用户确认，才是对的。

**另一例**：汇报里写"直播流量走这张流量包"，查代码后发现直播走的是独立的流媒体服务（独立域名、独立计费），与服务器流量包无关。**推断写进老板会看的文档前，必须先在物料里验证。**

## 三、结构与篇幅

### 3.1 骨架

```
# [结论式标题]                        ← 见 5.1，不带旁枝细节

编制：姓名（职务）
编制日期：YYYY-MM-DD

摘要                        ← 3–5 段，可独立阅读
一、判断与建议              ← 要老板做什么，逐条列出
二、背景与现状 ……           ← 视场景增减，按"事项"而不是按"六段"分章
…
末章、请示事项              ← 人 + 事 + 期限 + 不批的后果
```

**章节按事项分，不按方法论分。** 采购类汇报的天然章节是新购了什么、续费了什么、配套是什么、新增的是什么、为什么新增、钱怎么付、未来节奏。硬套"风险与应对"这种模板章，会让老板读到一段没有内容的段落。

### 3.2 篇幅：正文 800–1500 字（不含表格）

超过上限，几乎只有两种原因：①在解释技术而不是在讲生意；②在重复同一件事。**两种都是删。**

三处最容易超标：

1. **根因讲了超过一段。** 老板要知道"为什么会这样"到能认可这件事该做，就够了。
2. **收益写成"显著/大幅/明显"。** 这是字数在膨胀、信息在归零的信号。
3. **承诺和计划段落。** "每两周汇报一次""三个工作日内提交实施计划"——**这些是你的作业，不是他的决策依据。** 最多留一条老板能自己验证的指标。

**细节移到表格或附录，正文就干净了。** 表格不占正文篇幅，是这份文档里最经济的载体。

### 3.3 表格化优先

凡是"多项并列、各自金额或用途不同"的内容，一律用表：

| 用途 | 写法 |
|---|---|
| 采购构成 | 类别 / 内容 / 金额 / 说明 四列 |
| 各类资源干什么用 | 项目 / 用途 / 金额 三列，一行一项 |
| 时间与节奏 | 时间 / 需求判断 两列 |
| 新旧方案对比 | 原来 / 现在 / 差额 |

**表格的每一行都要回答"它用来干什么"**，不能只有名称和金额——老板看不懂产品名。

## 四、独立成文

**汇报是单独发出去的一份文件，不是知识库里的一个链接节点。**

| 禁止 | 替代做法 |
|---|---|
| "详见《XX 方案》第 3 章" | 把那一段的结论**原样写进**本文 |
| "参见上次汇报" | 把需要的背景重新陈述一遍 |
| "附件里有详细报价" | 把关键数字直接进表，明细才进附录 |
| "引用自 XX 文档" | 直接陈述事实，不标注来源文档名 |

**唯一允许的外部指针是给老板的实物凭证**（报价单号、订单截图、合同编号）——因为那是他要核对的对象，不是他要读的文档。

引用外部方案的内容时要**改写成本文的陈述句**：方案里写"建设某类统一平台、连接多类设备与数据"，汇报里就写成完整的陈述句——"我们的目标是建设一个覆盖多类设备与数据的统一平台"，后面接它和这笔钱的关系。

## 五、正式文风

正式不等于客套。**"尊敬的各位领导，恳请批示"是旧式公文，不是正式。** 正式的本质是**减少你和老板之间的解释成本**。

### 5.1 标题陈述结论

- ✗ 关于技术架构升级的汇报
- ✗ 关于年度设备采购与维护的请示（其中新增某型号 900 元）← **标题里不要塞次要细节，那属于摘要**
- ✓ 关于年度设备采购与维护的请示

### 5.2 七条硬规矩

1. **每段先立判断，再给依据。** 段首第一句必须是结论。
2. **数字必然带得出口径。** 来源单据、时点、是官网价还是折后价、是单台还是合价。老板质疑某个数时你能立刻说清来历，整篇可信度都上去。
3. **责任到人。** "相关同学跟进"是负面词；写成"由张三负责，4 月 10 日前完成，验收标准为 XX"。
4. **短句、主谓宾、动词开头。** 一句超过 40 字就拆开。
5. **少用人称代词**，多用"建议""应当""需由……负责"。
6. **不确定性必须如实交代。** 该说"待确认"就说"待确认"，该给区间就给区间；**但只在风险真实存在时才写风险**（见 6.3）。
7. **不替老板表态，不自我注脚，不稀释判断。** "这说明各级同事都不容易""作为技术负责人我必须如实说明""基本能覆盖"——三句话全部删。

### 5.3 必须清掉的 AI 腔与推销腔

这份文档最常见的失败不是写得太浅，而是**读起来像一个 AI 在推销一个方案**。逐项搜，见到就删：

| 类别 | 病灶词 | 改法 |
|---|---|---|
| **劝服腔** | 关键一步、真正需要、性价比最高、核心竞争力、唯一的选择、值得投入 | 改陈述：这件事的作用是什么，数字是多少 |
| **金句式总结** | "一句话总结：……""落到三句话：" | 删掉引导句，直接说内容 |
| **强行比喻** | 生产车间、零件库、标准件、质检员、档案室、护城河、地基 | 只在确实更好懂时用，且一个文档不超过一个比喻 |
| **双重强调** | "这不是小钱，而是……""金额虽小，但……" | 写成一个判断句 |
| **元话语** | 下面专门说明、正如上文所述、需要说明的是、值得一提的是 | 直接写内容 |
| **空泛程度词** | 本质是、完全、彻底、大幅度、一定程度上 | 删除或换成具体量 |

**自检办法**：把摘要单独抽出来读一遍。如果它读起来像广告文案而不是事实陈述，重写。

### 5.4 措辞对照

| 口语 / AI 腔 | 正式 |
|---|---|
| 我觉得应该做 | 建议实施 |
| 老板您看能不能 | 请予审批 |
| 要 2 个人 | 需增配后端工程师 2 名 |
| 大概 8 周 | 预计 8–10 周，以采购到位为前置条件 |
| 这笔钱花得非常值 | 该投入产出比为本年度最高，占总额 1.8% |
| 帮我们协调一下 | 请协调采购部门于 3 月 20 日前完成审批 |
| 取得了一定进展 | 完成 6 项里程碑中的 4 项 |

**规律：把"希望、努力、尽量、非常"换成"负责、完成、审批"。前者是愿望和情绪，后者是责任和事实。**

## 六、每段写什么

### 6.1 摘要 —— 三个问题

1. **要多少钱 / 要什么**，原价多少、实付多少、省多少
2. **这笔钱做几件事**，逐条列出，各自金额
3. **哪一项需要老板特别判断**，以及它为什么值得单独看

### 6.2 判断与建议 —— 逐条，每条一个动词

```
1. 建议批准本次采购。存量续费为刚性支出，不续则业务中断；新增部分为后续建设的前置条件。
2. 建议确认新增设备的必要性。它是……的基础，越晚投入，历史包袱越重。
3. 建议确认付款方式。……执行方式为……
```

### 6.3 风险段：能不写就不写

**只有风险真实存在可观敞口时才写，且最多三条**，每条固定格式：风险是什么 → 如果发生 → 我会怎么办。

**以下四种情况不写风险段**，改用一句前置说明即可：

| 情况 | 写法 |
|---|---|
| 合作关系已稳定、敞口已被流程控制 | 一句话说明控制方式（如"先充 2 万，到账后补足"），不另设风险章 |
| 用户明确要求不铺开风险 | 照办；风险确实重大时口头提醒，不写进文档 |
| 风险已被降价、折扣、备份等措施覆盖 | 把措施写进正文对应章节，不单独成节 |
| 写出来只是"订单会取消""明年要续费"这类流程常识 | 删。那不是风险，是常识 |

**绝不写"最坏情况是钱打水漂"这种吓人的假设**——除非用户确认这个敞口真实存在，并且他要求写。

### 6.4 请示事项 —— 只报一个方案

**能确定执行方式时，不要给老板出选择题。** 选择题把决策难度退还给老板，而方案细节你比他清楚。

- ✗ A. 批准全额 / B. 先批 2 万试跑（请二选一）
- ✓ 请于 X 月 X 日前批准金额 Y，并确认执行方式：**先做 [步骤一]，完成后立即 [步骤二]**。

只有**两条路径真的代表不同的钱、不同的人、不同的风险**时，才给选项，且必须标出推荐项。

**末段固定元素**：金额 + 执行方式 + 期限 + **不批的后果**。

## 七、让老板看懂技术

### 7.1 三件套：它是什么 → 解决什么 → 不解决会怎样

技术名词单独出现等于没写。每个概念必须同时给出这三层，且顺序固定：

```
GitLab 代码仓库 → 代码统一托管，每次改动的提交人、时间、内容均可追溯 → 否则无法确认哪一份在线上运行
```

### 7.2 先答"能不能不用"，再答"为什么非要"

老板看到一笔技术投入，第一反应往往是"这事不能凑合吗"。**直接把这个疑问写进文档当小标题**，比它被当面问出来好：

```
### 6.1 代码只存在个人电脑与网盘中的问题
当前代码主要存放在个人电脑与网盘、移动硬盘中。这种方式在单人阶段可以运转，但无法支撑团队协作与客户交付，具体表现在三个方面。
**版本无法追溯。** ……
**发布不可控。** ……
**多人无法协同。** ……
```

**三个问题各一段，每段结尾落到一个后果**（客户侧故障无法止损、无法证明改的是客户要的那一版、人员变动时代码可能拿不全）。后果落在**公司资产和客户**上，不落在工程师的不便上。

### 7.3 技术介绍压到最小可理解单位

研发环境、工程底座、Git 工作流这类内容，老板只需要知道**它管什么、不管会怎样**。

- 四项能力 → 一张四行表（名称 / 作用）
- 工作流 → 四条规则、两句话价值，不超过 300 字
- 不要展开架构图、不要讲选型理由、不要讲替代方案对比

**篇幅标准：老板读完能向第三个人复述这件事有什么用，就够长了。**

## 八、写完之后

### 8.1 自检清单（任何一条不过就改）

- [ ] 摘要单独读，老板能拍板、能复述吗？
- [ ] 有没有一个数字是自己算的而不是从单据来的？**有就回去算**
- [ ] 全文有没有"详见/参见/引用自/附件里有"这类外部指针？
- [ ] 有没有 AI 推销腔（5.3 表逐项搜）？
- [ ] 每个技术名词是否都有"是什么 → 解决什么 → 不解决会怎样"？
- [ ] 每个金额是否都能对上单据，且口径写明（官网价/折后/单台/合价）？
- [ ] 有没有"显著提升""大幅改善""一定程度上"？
- [ ] 请示事项是否只有一个方案、含期限、含不批的后果？
- [ ] 有没有写"下一步我会怎么做""每两周汇报一次"？（删到最多一条）
- [ ] 有没有"相关同学""努力推进"？
- [ ] 有没有甩锅、诉苦、抱怨别的部门？

### 8.2 交付与归档

- **只交付定稿**。不要交"带待确认标记的版本"再改——**待确认项要么落实，要么删掉**。
- **不写版本号**。定稿即覆盖同名文件，版本历史交给 git；需要措辞迭代时直接改原文件。
- 交付后主动列出**仍需用户核实的两个数**（如果有），让他一次性确认，而不是等他发现。
- 归档时同步更新所在目录的 `README.md`（内容清单 + 检索指引），否则等于没归位。

---

## 九、当面汇报

**前 30 秒定成败。** 开场三句话，只讲这个顺序：

> "老板，有件事需要您拍板。"
> "现在不做，[他能感知到的事]大概率会[发生]。"
> "我建议做，要 [X]，[多久]，能[具体结果]。"

**说完停住，看他反应。** 他追问的那个问题，就是接下来要重点讲的。

**准备三层深度，只讲第一层。** 他问"为什么要两台"，你答"这两台配置一样，一台跑生产一台跑研发，分开是为了互不影响"——不答架构，答他的疑问。

## 十、与其他框架的关系

Scrum 的 Inception 只提供**素材**（为什么做、范围、验收标准、风险），不提供**汇报形式**。开完 Inception 后按本方法重写一遍，不要把 Inception 产出物直接发给老板。

**不要把 Sprint Review、Burndown 这类敏捷术语带进汇报。** 老板不需要知道什么是 Sprint，他只需要知道"这个月底会交付什么、会不会变好"。

立项申请、进度汇报、事故复盘、年度规划四种场景的骨架见 [references/TEMPLATES.md](references/TEMPLATES.md)。选最接近的用，不要硬套。
